# 語の追加前検証

**このスキルは調べるだけで、ファイルを一切書き換えない。** 実装は `entry-add` の担当。
分けてあるのは、検証を省いて書き始める事故を防ぐため。

このプロジェクトの価値は「出典つきで、推測で断定しない」ことにある。
検証を飛ばして書いた1語が、その価値を丸ごと損なう。

## 入力の受け取り方

**単語を渡された場合** — そのまま用語として扱う。

**issue 番号 / issue の URL を渡された場合** — 先に中身を取る。

```bash
gh issue view <番号> --json number,title,body,labels
```

issue フォームの本文は `### <ラベル>` 区切りの Markdown。`_No response_` は未入力。

| ラベル | 意味 |
| --- | --- |
| 用語 | 追加・修正の対象 |
| 読み方（分かる場合） / 正しいと思う読み | 報告者の主張。**鵜呑みにしない。裏を取る対象** |
| 現在の掲載 | `fix` ラベルのとき。既存エントリの修正依頼 |
| 出典 URL | あれば必ず検証する。無くても進めてよい |
| 補足 | 現場での呼ばれ方など。divergence の判断材料 |

ラベルが `entry` なら追加、`fix` なら既存エントリの修正。**`fix` は新規追加ではない**ので、
対象エントリを特定してから差分を提案する。

## 手順

### 1. 重複を調べる

```bash
node .claude/skills/entry-verify/scripts/check-duplicate.mjs "<用語>" "<読みのカタカナ>"
```

slug / term / aliases / ja[].kana の4つを見る。**term だけ見ると取り逃す。**
実例: 「Golang」を追加しようとすると、`Go`（slug が `golang`、aliases に `Golang`）に当たる。

`generated/entries.json` が無いと動かない。その場合は先に `pnpm run data`。

重複していたら**そこで止める**。実装に進まず、既存エントリへの追記・修正として提案する。

### 2. 公式サイトを特定して検証する

```bash
node .claude/skills/entry-verify/scripts/verify-url.mjs "<URL>" "<用語>"
```

見るのは3点。

- **HTTP 200 が返るか**
- **リダイレクト後も同じホストか**（別サイトに飛んでいたらその URL は使わない）
- **用語がページに現れるか**（0回なら取り違え）

`homepage` は「その物の入口」。**`sources`（読みの根拠）とは別物**なので混ぜない。
JWT の出典は RFC、PNG の出典は W3C の仕様書で、どちらも公式サイトではない。

GitHub リポジトリしか無い場合はそれを `homepage` にしてよい。

### 3. 読みの出典を探す

公式ドキュメントの FAQ、README、仕様書に読みが書かれていることがある。
`verify-url.mjs` が「読みに言及していそうな文」を抜き出すので、**その中の文をそのまま使う。**

```
読みに言及していそうな文:
  - Django is pronounced JANG -oh.
```

**quote には原文をそのまま入れる。要約・翻訳・再構成をしたものを quote にしない。**
出典が見つからないのは失敗ではない。見つからなければ `needsSource: true` で載せる。
これはこのプロジェクトが認めている正規の状態。

`kind` の選び方:

| kind | 使う場面 |
| --- | --- |
| `author` | 作者本人の発言。最も強い |
| `official` | 公式サイト・公式リポジトリの README |
| `docs` | 公式ドキュメント・仕様書（RFC など） |
| `conference` | 講演 |
| `community` | それ以外。OWASP のような団体の記述を含む |

### 4. 日英のズレを判定する

`divergence: true` は**このプロジェクト最大の差別化点**なので、安易に付けない。

付けるのは「英語圏の読みと日本の現場の読みが食い違っていて、どちらで喋るか迷う」場合だけ。
発音記号の細かい差ではない。

- 付ける例: JWT（仕様は "jot"、日本は「ジェイダブリューティー」）
- 付けない例: Python（パイソン。英語圏と実質同じ）

付けるなら `divergenceNote` に「何が、どうズレているか」を必ず書く。lint が警告する。

### 5. 確度を決める

| confidence | 条件 |
| --- | --- |
| `high` | 出典があり、読みが1つに定まる |
| `medium` | 出典は無いが、読みはほぼ揺れない |
| `low` | 推測に近い。`herdr` のように綴りからの解釈しかない |
| `disputed` | 読みが実際に割れている。複数の読みを併記する |

**出典なしで `high` は付けない。** lint が警告する。

## 出力

最後に検証レポートを出す。`entry-add` はこれを入力として受け取る。

```
## 検証レポート: <用語>

- 重複: なし / あり（→ /w/<slug>/）
- 公式サイト: <URL>（HTTP 200・用語 N 回・同一ホスト）/ 見つからず
- 読みの出典: <URL>（kind: docs）/ 見つからず → needsSource
  引用: "<原文のまま>"
- 読み: <カタカナ>（primary）、他の候補
- 英語: respelling / ipa / note
- カテゴリ: <CATEGORIES のどれか>
- 日英のズレ: あり（理由）/ なし
- 確度: <confidence>（理由）
- 判定: 追加してよい / 重複のため見送り / 既存の修正として扱う
```

## やってはいけないこと

- **URL を推測で書く。** 必ず `verify-url.mjs` に通す。200 が返っても用語が出てこなければ採用しない
- **403 で確認できなかった URL を採用する。** 「取得できない」は「正しい」ではない
- **quote を作文する。** ページに書かれていない文言を出典として引用しない
- **読みを断定する。** 確認できていないなら `needsSource: true` と `confidence` で正直に表す
